Аудит защиты от SQL-инъекций

Смотрел все места, где приложение ходит в базу: добавление и редактирование партнера, реестр, история реализации, расчет материалов. Полей поиска и авторизации в приложении нет.

Приложение/partners.js, строки 71, 76, 81, 86. Выборка, вставка и обновление партнера. Все данные из формы уходят аргументами ($1 и дальше), в текст запроса ничего не подставляется. В строках 71 и 76 запрос склеивается из двух постоянных кусков, пользовательских данных в склейке нет, id партнера идет параметром.

Разработка интерфейса истории реализации продукции/history.js, строка 12. partner_id из адресной строки уходит параметром $1.

Разработка ядра алгоритма расчета материалов/materials.js, строки 24 и 25. Id типов уходят параметрами, перед запросом проверяются на целое число.

Приложение/api.js. Id партнера вынимается из адреса регулярным выражением и принимается только числом до девяти цифр, иначе запрос отклоняется.

Интеграция метода расчета и комплексное тестирование/calculator-api.js, строки 13 и 14. Запросы к справочникам постоянные, пользовательские данные в них не попадают вообще. Числа из калькулятора уходят дальше в метод расчета и там идут параметрами.

Итог: Конкатенации пользовательских данных в SQL нигде нет. Плюс текст от пользователя попадает на страницу только через textContent, то есть html или скрипт в карточку не вставить.

Выходит, от SQL-инъекций защита есть. Проверил все вызовы query в коде, их десять, и в каждом данные идут отдельными аргументами, а текст запроса собирается только из постоянных кусков.
